Automated COD Settlement & Bulk RV API Web App

Bypassing ERP UI limitations to streamline high-volume Cash On Delivery (COD) payment postings (10,000+ monthly invoices) from 3rd-Party Logistics (3PL) carriers. ก้าวข้ามข้อจำกัดหน้าจอระบบ ERP เพื่อเคลียร์บิลรับชำระเงินเก็บปลายทาง (COD) ปริมาณสูง (กว่า 10,000 รายการต่อเดือน) จากบริษัทขนส่ง (3PL) แบบอัตโนมัติผ่าน REST API

1. Gap Analysis & The Business Challenge 1. การวิเคราะห์ปัญหาและข้อจำกัดของระบบเดิม (Gap Analysis & Business Challenge)

The Core Problem: The company processes over 10,000 Cash On Delivery (COD) invoices monthly across multiple 3rd-Party Logistics (3PL) carriers, where each carrier remittance covers thousands of individual invoices. While TRCloud ERP provides a standard bulk payment clearing screen using internal sales filters (Date, Invoice Number, or Customer ID), it cannot query or cross-reference invoices based on external 3PL settlement report parameters—rendering the native bulk receipt feature unusable for COD settlements.

ปัญหาหลักทางธุรกิจ: บริษัทมีรายการใบแจ้งหนี้แบบเก็บเงินปลายทาง (COD) มากกว่า 10,000 รายการต่อเดือนผ่านบริษัทขนส่ง (3PL) หลายเจ้า โดยการโอนเงินคืนแต่ละรอบของขนส่งจะรวบยอดบิลมาหลายพันใบ แม้ระบบ TRCloud ERP จะมีฟังก์ชันรับชำระเงินแบบกลุ่ม (Bulk Payment) แต่ตัวกรองบนหน้าจอรองรับเฉพาะฟิลด์การขายมาตรฐาน (วันที่, เลขที่ใบแจ้งหนี้, รหัสลูกค้า) ไม่สามารถกรองหรืออ้างอิงตามพารามิเตอร์ในไฟล์รายงานการโอนเงินของขนส่ง (3PL Settlement Report) ได้ ทำให้ไม่สามารถใช้ฟังก์ชันมาตรฐานของ ERP ในการตัดรับชำระเงิน COD ได้เลย

As-Is (Manual Workflow & Pain Points) As-Is (กระบวนการทำงานแบบเดิม)

  • Native ERP filters cannot retrieve unpaid invoices based on external 3PL settlement files.
  • When 3PLs transfer lump-sum payouts, finance staff must manually search, match, and clear invoices one by one across massive datasets.
  • Severe operational bottleneck taking several days per billing cycle with high risk of human entry errors.
  • ตัวกรองบนหน้าจอ ERP ไม่สามารถดึงใบแจ้งหนี้ค้างชำระตามรายชื่อในไฟล์สรุปยอดโอนของขนส่ง (3PL) ได้
  • เมื่อขนส่งโอนเงินก้อนเข้ามา พนักงานการเงินต้องค้นหา จับคู่ และกดตัดรับชำระบิลทีละใบจากข้อมูลนับหมื่นรายการ
  • เกิดคอขวดรุนแรง ใช้เวลาหลายวันต่อรอบการโอน และมีความเสี่ยงสูงที่จะคีย์ข้อมูลผิดพลาด

To-Be (Automated System Integration) To-Be (โซลูชัน Web App & REST API อัตโนมัติ)

  • Developed a custom Middleware Web App that completely bypasses the ERP's UI filtering limitations.
  • Seamless Upstream Hand-off (Tab: PostToRV): Users copy the pre-reconciled table—PaidDate/Customer (formatted as ddMMyyyy + 3PL Code + 3PL Payment Run#, e.g., 07112025DHL6, to separate each lump-sum payment batch), InvoiceNumber, and Amount (filtered via TRCloud Status = Debtor)—directly from the 3-Way AR Reconciliation Tool and paste it into the Web App.
  • The backend automatically aggregates records, constructs an accounting-compliant JSON payload with MD5 authentication, and batch-posts Receipt Vouchers (RV) via REST API in a single step.
  • พัฒนา Middleware Web App เฉพาะทางเพื่อก้าวข้ามข้อจำกัดด้านการกรองข้อมูลบนหน้าจอ ERP โดยสมบูรณ์
  • เชื่อมต่อข้อมูลต่อจากชีท PostToRV ทันที: ผู้ใช้งานเพียง Copy ตารางข้อมูล—ซึ่งประกอบด้วย PaidDate/Customer (วันที่รับชำระ ddMMyyyy + รหัส 3PL + เลข Run ก้อนการโอน เช่น 07112025DHL6 เพื่อใช้แยกก้อนชำระเงิน), InvoiceNumber และ Amount (ที่กรองเฉพาะสถานะ Debtor จาก TRC แล้ว)—จากโปรเจกต์ Automated 3-Way AR Reconciliation มาวาง (Paste) ลงในหน้าเว็บแอปโดยตรง
  • ระบบรวบรวมข้อมูล สร้าง JSON Payload ตามมาตรฐานบัญชี เข้ารหัสความปลอดภัย MD5 และยิงสร้างใบสำคัญรับ (RV) แบบกลุ่มผ่าน REST API เสร็จสิ้นในคลิกเดียว

2. System Architecture & Data Pipeline 2. สถาปัตยกรรมระบบและขั้นตอนการประมวลผล (System Architecture & Flow Process)

Continuing directly from the PostToRV tab of the 3-Way AR Reconciliation Tool (which pre-filters TRCloud invoices using Status = Debtor to prevent duplicate RV creation), finance staff copy the 2-column table (InvoiceNumber, and Amount) and paste it into the Frontend (HTML/JS). Following instant validation, the Backend (Google Apps Script) constructs a structured JSON payload, generates an MD5 encryption signature for API authentication, and executes a REST API POST request to TRCloud ERP—generating Receipt Vouchers (RV) that clear hundreds of invoices in under 2 seconds while logging audit trails to Google Sheets.

ต่อเนื่องโดยตรงจากแท็บ PostToRV ในโปรเจกต์ Automated 3-Way AR Reconciliation (ซึ่งกรองเอาเฉพาะอินวอยซ์ที่มี Status = Debtor จากข้อมูล TRC เพื่อป้องกันการโพสต์ RV ซ้ำ) พนักงานการเงินเพียงคัดลอกข้อมูล (InvoiceNumber และ Amount) มาวางบน Frontend (HTML/JS) จากนั้น Backend (Google Apps Script) จะจัดโครงสร้าง JSON Payload สร้างรหัสรับรองความถูกต้องแบบ MD5 และยิงคำสั่ง REST API POST เข้าสู่ TRCloud ERP เพื่อออกใบสำคัญรับ (RV) ล้างหนี้หลายร้อยบิลภายในเวลาไม่ถึง 2 วินาที พร้อมบันทึก Transaction Log ลงฐานข้อมูล Google Sheets อัตโนมัติ
